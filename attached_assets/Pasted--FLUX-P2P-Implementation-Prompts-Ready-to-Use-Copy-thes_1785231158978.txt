```
### PROMPT 3.1: File Transfer State Machine

**For Backend/Reliability Engineer:**

```
Implement production-grade file transfer with state management,
checksum verification, and resume capability.

REQUIREMENTS:

1. File Transfer State Machine:
   
   States: QUEUED → UPLOADING → UPLOADED → VERIFYING → COMPLETE → ARCHIVED
   Also: QUEUED → PAUSED → UPLOADING → ...
   Error path: Any state → ERROR (with retry logic)
   
   Transitions:
   QUEUED → UPLOADING (when peer available)
   UPLOADING → PAUSED (user pause or network timeout 30s)
   PAUSED → UPLOADING (user resume)
   UPLOADING → UPLOADED (all chunks received)
   UPLOADED → VERIFYING (checksum validation)
   VERIFYING → COMPLETE (hash matches)
   VERIFYING → ERROR (hash mismatch, offer retry)
   COMPLETE → ARCHIVED (1 hour after completion)
   ERROR → QUEUED (retry after exponential backoff)

2. Chunking Strategy:
   
   Design:
   - Chunk size: 64 KB (65536 bytes)
   - Header: [magic:4][version:1][fileId:16][chunkSeq:4][totalChunks:4]
   - Payload: up to 65536 bytes
   - Footer: [crc32:4]
   - Total per chunk: ~65556 bytes
   
   Max concurrent chunks: 4 per file
   - Prevents overwhelming network
   - Balances parallelism vs latency
   
   Chunk ordering:
   - Sender transmits in sequence (0, 1, 2, ...)
   - Receiver accepts out-of-order
   - Stores in Map<chunkSeq, buffer>
   - Track chunks received in BitSet

3. File Metadata:
   
   ```typescript
   interface FileTransfer {
     id: string  // UUID
     name: string
     size: number  // bytes
     mimeType: string
     hash: {
       algorithm: 'sha256'
       value: string
     }
     created: timestamp
     lastActivity: timestamp
     state: TransferState
     
     sender: {
       peerId: string
       uploadedBytes: number

     }
   ```

4. Checksum Verification:
   
   Flow:
   a) Sender computes SHA-256 of file before split
   b) Send in fileMetadata: {"hash": "abc123..."}
   c) Receiver accumulates chunks
   d) After all chunks received, compute SHA-256
   e) Compare: If match → COMPLETE, else → ERROR
   
   Edge cases:
   - Partial file received (missing chunks) → Error immediately
   - Corrupted chunk detected (CRC32 fail) → Request retransmit
   - Network corruption unlikely with WebRTC but still check

5. Resume Capability:
   
   Store in IndexedDB:
   ```
   Database: flux_transfers
   Store: transfers
   Key: fileId
   Value: {
     fileId, fileName, fileSize, hash,
     chunksReceived: [0, 1, 2, 5, 6, ...],
     localPath, timestamp
   }
   ```
   
   On disconnect:
   - Save state to IndexedDB
   - Show "Transfer paused" UI
   - Save for 24 hours
   
   On reconnect:
   - Query IndexedDB
   - Show "Resume transfer?" prompt
   - Resume from last missing chunk
   - Send: {"action": "resume_transfer", "fileId": "...", "lastChunk": 42}
   - Receiver responds with next chunk needed

6. Bandwidth Awareness:
   
   Adaptive chunk size:
   - Start with 64 KB
   - Monitor RTT and packet loss
   - If loss > 5%: reduce to 32 KB (less retransmit overhead)
   - If loss < 1% and RTT < 50ms: increase to 128 KB
   - Every 10 chunks: re-evaluate
   
   Monitoring:
   ```typescript
   interface NetworkCondition {
     rtt: number  // round trip time ms
     packetLoss: number  // 0-1 (0.05 = 5%)
     bandwidth: number  // bytes/sec estimate
   }
   
   function getOptimalChunkSize(cond: NetworkCondition): number {
     if (cond.packetLoss > 0.1) return 16384  // 16 KB
     if (cond.packetLoss > 0.05) return 32768  // 32 KB
     if (cond.packetLoss < 0.01 && cond.rtt < 50) return 131072  // 128 KB
     return 65536  // Default 64 KB
   }
   ```

7. Error Handling & Retries:
   
   Chunk transmission failures:
   - First failure: Retry immediately
   - Second failure: Wait 500ms, retry
   - Third failure: Wait 2s, retry
   - Fourth failure: Move to ERROR state, notify user
   
   Corrupted chunks:
   - On CRC32 mismatch: Mark chunk as failed
   - Request retransmit within 3 seconds
   - After 3 retries: Likely media corruption, error out
   
   Network timeout:
   - No chunk received for 30 seconds → Pause transfer
   - Show: "Transfer paused due to inactivity"
   - User can resume within 24 hours
   
   User abort:
   - Move to ERROR state
   - Clean up IndexedDB
   - Show: "Transfer cancelled"

8. Progress Tracking UI:
   
   ```typescript

     bytesTransferred: number
     totalBytes: number
     currentSpeed: number  // KB/s
     estimatedTimeRemaining: number  // seconds
     
     chunkStatus: {
       current: number  // Current chunk being sent/received
       total: number
       completed: number
     }
     
     errors?: {
       count: number
       lastError: string
     }
   }
   ```

9. Backend Tracking (Firestore):
   
   Collection: transfers/{transferId}
   - Store metadata for resumed transfers
   - TTL: 24 hours (auto-delete after expiry)
   - Query: "Show my recent transfers"

10. Testing Strategy:
    
    Unit tests:
    - Chunk creation/parsing
    - Hash computation
    - State transitions
    
    Integration tests:
    - 10 MB file end-to-end
    - Pause/resume in middle

    - Measure memory usage
    - Identify bottlenecks
