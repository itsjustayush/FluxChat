## 🚨 CRITICAL ISSUES (Must Fix Before Scale)

### ISSUE #1: Single STUN Server with No TURN Fallback
**Severity:** CRITICAL  
**Impact:** 30-40% of users behind strict firewalls unable to connect

**Current State:**
```javascript
stun:stun.l.google.com:19302  // Single point of failure
```

**Problem:**
- No TURN relay for symmetric NAT/firewall scenarios
- Google STUN server is unreliable in corporate environments
- No fallback if primary STUN fails
- No latency monitoring for STUN server health

**PROMPT FOR FIX:**
```
Create a production-grade STUN/TURN configuration module:

1. Implement COTURN server failover with 3 geographically distributed TURN servers
2. Design a STUN server health-check system that:
   - Pings STUN servers every 30 seconds
   - Automatically rotates to backup if latency > 500ms or failure rate > 5%
   - Logs server performance metrics
3. Add configuration for these backup STUN servers:
   - stun.stunprotocol.org:3478
   - stun1.l.google.com:19302
   - stun.services.mozilla.com:3478
4. Create RTCConfiguration factory that dynamically builds ICE candidates list
5. Add WebRTC stats monitoring to track ICE candidate types used
6. Document fallback behavior in technical runbook

Deliverable: src/lib/iceServerManager.ts with:
- getOptimalICEServers() function
- iceServerHealthMonitor() background task
- metrics collection for analytics
```

### ISSUE #2: Missing Signal Server Architecture
**Severity:** CRITICAL  
**Impact:** Cannot establish P2P connections at scale

**Problem:**
- SDP offer/answer exchange mechanism not documented
- No mention of signaling server for initial peer discovery
- Unclear how Room OTP translates to actual peer connections
- No session description protocol handling details

**Current Assumption (Dangerous):**
The document vaguely implies browser-only solution, but WebRTC requires a signaling layer to exchange SDP offers/answers before direct P2P channels open.

**PROMPT FOR SIGNALING LAYER:**
```
Design and implement a lightweight signaling server:

1. Architecture Decision:
   - Option A: WebSocket relay (Node.js + Socket.io)
   - Option B: Firebase Realtime Database (serverless)
   - Option C: Hybrid (WebSocket primary, Firebase fallback)
   
   Recommend: Option C for resilience
   
2. Signal Server Responsibilities:
   - Maintain room registry (room_id → [peer_ids])
   - Relay SDP offers/answers between peers
   - Handle ICE candidate trickling
   - Track peer connection state
   - Clean up stale rooms after 30 min inactivity

3. Client-Side Integration:
   - Create SignalClient class that:
     * Establishes persistent WebSocket to signal server
     * Emits room-join with OTP
     * Listens for peer-discovered events
     * Relays SDP offers/answers to WebRTCPeerEngine
   
4. Security:
   - Sign all signals with HMAC-SHA256 using room secret
   - Rate limit signal operations per peer (10 req/sec max)
   - Validate SDP format before relaying (prevent injection)

5. Testing:
   - Write load test: 100 rooms × 10 peers = 1000 connections
   - Measure signal latency p50/p95/p99
   - Test failover between WebSocket and Firebase

Deliverable: 
- src/lib/signalClient.ts
- /signals-server (new backend folder)
- test/signaling.load.test.ts
```

### ISSUE #3: Undefined Room Lifecycle & Cleanup
**Severity:** CRITICAL  
**Impact:** Resource leak, DoS vulnerability, unpredictable behavior

**Problem:**
- No mention of room timeout/expiration
- No cleanup of stale peer connections
- Unclear if rooms are ephemeral or persistent
- No mention of max concurrent peers per room
- "Ephemeral" is claimed but mechanism undefined

**PROMPT FOR ROOM LIFECYCLE MANAGEMENT:**
```
Implement complete room lifecycle with automatic cleanup:

1. Room State Machine:
   States: PENDING → ACTIVE → EXPIRING → CLOSED
   
   - PENDING (0-2 min): Room code generated, awaiting first peer join
   - ACTIVE (max 4 hours): Multiple peers connected, file transfers allowed
   - EXPIRING (30 sec warning): No data activity for 30 min, inform peers
   - CLOSED: All peers disconnected OR timeout reached

2. Automatic Cleanup Rules:
   - Room auto-deletes if:
     * 0 peers for > 5 minutes
     * Any single room active for > 4 hours (hard limit)
     * Total room age > 24 hours (safety limit)
   - Warn connected peers 30 seconds before deletion
   - Send leave notification to all peers

3. Per-Room Constraints:
   - Max 50 concurrent peers (raise error if exceeded)
   - Max 5 GB total data transfer per room
   - Max 10 concurrent file uploads per room

4. Room State Tracking:
   Create RoomManager class:
   ```typescript
   class RoomManager {
     createRoom(options: RoomOptions): Room
     joinRoom(roomId: string, peerId: string): Room
     leaveRoom(roomId: string, peerId: string): void
     getRoomStats(roomId: string): RoomStats
     cleanupExpiredRooms(): void  // Run every 60 seconds
   }
   ```

5. Backend Tracking:
   Store in Firestore:
   - rooms/{roomId}/{metadata, createdAt, lastActivityAt, peers}
   - Implement TTL document deletion policy

6. Frontend Cleanup:
   - On window beforeunload, call leaveRoom()
   - Monitor connection state, auto-cleanup if DISCONNECTED > 2 min
   - Display countdown timer when room expiring

Deliverable:
- src/lib/roomManager.ts
- src/lib/roomStateChart.ts (state machine)
- src/hooks/useRoomLifecycle.ts
- Firestore rules for TTL
```

### ISSUE #4: No Input Validation or Rate Limiting
**Severity:** HIGH  
**Impact:** Security vulnerability to injection, DoS

**Problem:**
- Room OTP never validated format (should be alphanumeric only)
- QR code parameters (?room=, ?action=) not sanitized
- No rate limiting on room join attempts
- No CSRF token on deep links

**PROMPT FOR SECURITY HARDENING:**
```
Implement comprehensive input validation and rate limiting:

1. OTP Validation Layer:
   - Room OTP regex: ^[A-Z0-9]{6}$ (exactly 6 alphanumeric)
   - Validate on client (UX) and server (security)
   - Reject invalid OTP with specific error (not generic)
   - Log failed attempts for security monitoring

2. URL Parameter Sanitization:
   ```typescript
   function validateRoomParams(url: URL) {
     const room = url.searchParams.get('room')
     const action = url.searchParams.get('action')
     
     if (room && !/^[A-Z0-9]{6}$/.test(room)) throw InvalidRoomError
     if (action && !['download_bundle'].includes(action)) throw InvalidActionError
     
     // Prevent open redirect
     if (url.origin !== window.location.origin) throw XSSError
   }
   ```

3. Rate Limiting (Per Browser):
   - Room join: 10 attempts per 60 seconds per IP
   - File upload: 100 MB per minute per peer
   - Download: 500 MB per minute per peer
   - Implement leaky bucket algorithm

4. Implement CSRF Protection:
   - Generate state token for QR-initiated joins
   - Store nonce in sessionStorage
   - Validate on room join callback

5. Content Security Policy (CSP):
   - Add CSP headers (no inline scripts)
   - Restrict video source to same-origin only
   - Disable unsafe-eval

Deliverable:
- src/lib/validators.ts
- src/lib/rateLimiter.ts
- middleware/security.ts
- CSP configuration
```

**Impact:** Silent failures, poor user experience, no debugging info

**Problem:**
- No try-catch around WebRTC connection establishment
- No error boundary for React components
- No fallback if encryption fails
- Error messages not user-friendly
- No retry logic for failed peer connections

**PROMPT FOR ERROR HANDLING:**
```
Create comprehensive error handling and recovery system:

1. WebRTC Connection Error Handler:
   ```typescript
   peerConnection.addEventListener('connectionstatechange', (event) => {
     switch(peerConnection.connectionState) {
       case 'connected': handleConnected()
       case 'disconnected': handleDisconnect(autoRetry=true)
       case 'failed': handleConnectionFailed(retryCount)
       case 'closed': handleClosed()
     }
   })
   ```
   
   On failed connection:
   - Attempt 3 retries with exponential backoff (1s, 2s, 4s)
   - Try alternate STUN/TURN servers
   - Notify user with estimated recovery time
   - Log error with session ID for debugging

2. Encryption Error Handler:
   - Catch crypto.subtle.encrypt failures
   - Attempt retry with new IV
   - If persistent, offer alternative (plain transfer with warning)
   - Log error signature for analysis

3. React Error Boundary:
   ```typescript
   class ErrorBoundary extends React.Component {
     componentDidCatch(error, errorInfo) {
       // Log to Sentry/LogRocket
       // Show user-friendly error UI
       // Offer recovery options
     }
   }
   ```

4. Error Classification & User Messages:
   - NETWORK_ERROR: "Lost connection. Reconnecting..."
   - CRYPTO_ERROR: "Encryption issue. Please refresh."
   - PERMISSION_ERROR: "Camera/microphone permission denied"
   - INVALID_OTP: "Room code not found or expired"
   - TIMEOUT: "Connection took too long. Please try again."

5. Recovery Strategies:
   - Auto-reconnect with exponential backoff
   - Offer manual room re-join
   - Cache last successful state
   - Implement checkpoint system for file transfers

Deliverable:
- src/components/ErrorBoundary.tsx
- src/lib/errorHandler.ts
- src/hooks/useConnectionRecovery.ts
- Error logging integration
```

### ISSUE #6: Missing File Transfer State Machine
**Severity:** HIGH  
**Impact:** Corrupted files, incomplete transfers, data loss

**Problem:**
- File chunking strategy not defined (size? retry logic?)
- No checksum verification mentioned
- No resume capability for interrupted transfers
- No progress tracking detailed implementation
- Chunk ordering/reassembly logic not specified

**PROMPT FOR ROBUST FILE TRANSFER:**
```
Design and implement production-grade file transfer system:

1. Chunking Strategy:
   - Chunk size: 64 KB (balances latency and overhead)
   - Max concurrent chunks: 4 per file
   - Sequence number + total chunks header
   
   Format:
   ```
   [magic:4][version:1][fileId:16][chunkSeq:4][totalChunks:4][payload:65536][crc32:4]
   ```

2. File Transfer State Machine:
   States: QUEUED → UPLOADING → UPLOADED → VERIFYING → COMPLETE
   
   Transitions:
   - On chunk error: backoff 1s, retry up to 3x
   - If > 30s without activity: pause transfer, prompt user
   - On completion: verify CRC32, move to VERIFYING
   - Store partial transfers in IndexedDB for resume

3. Progress Tracking:
   ```typescript
   interface TransferProgress {
     fileId: string
     bytesTransferred: number
     totalBytes: number
     percentComplete: number
     estimatedTimeRemaining: number
     chunksReceived: Set<number>  // For resume
     state: TransferState
   }
   ```

4. Checksum Verification:
   - Client generates SHA-256 hash before transfer
   - Send hash in file metadata
   - Receiver verifies after reassembly
   - Re-request individual chunks if hash mismatch

5. Resume Capability:
   - On disconnect: store chunks received in IndexedDB
   - On reconnect: query peer for missing chunks
   - Resume from last complete chunk
   - Timeout resume after 24 hours

6. Bandwidth Awareness:
   - Monitor RTT and packet loss
   - Auto-adjust chunk size if loss > 5%
   - Implement adaptive bitrate (start 64KB, adjust ±50%)

Deliverable:
- src/lib/fileTransferEngine.ts
- src/lib/chunkAssembler.ts
- src/hooks/useFileTransfer.ts
- tests/fileTransfer.test.ts
```
